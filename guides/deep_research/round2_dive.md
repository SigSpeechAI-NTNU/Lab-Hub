# Deep Research 第二輪：深挖選定路線（共用，v4.1，2026-10-08）

> 前置：先用 `round1_map.md` 跑完第一輪並核對，選定一條技術路線（研究生請先和指導教授討論過，見文末操作方法）。
> 這一輪的目的是**投出一篇學術會議論文**：依可用資料、GPU 與目標會議的截稿日，把路線收斂成可排序的具體題目與研究提案 one-pager。時程一律從截稿日倒推。教授與研究生共用同一份指令。
> 核對指令在 `round1_map.md`。〔〕內為每次要填的欄位。

## 第二輪指令

```
今天是〔YYYY-MM-DD〕，所有「近 N 年／近 N 個月」以此日期為基準。

延續上一輪對「〔細分題目，用第一輪報告 §1 確定的正式名稱〕」的研究（第一輪報告見附件），
我決定深挖「〔路線名稱，沿用第一輪報告的命名〕」這條技術路線，目標是投出一篇會議論文。
請做第二輪深度研究，讀者是我：已讀過第一輪報告。
不要重做第一輪 §1–3 的內容；需要時引用第一輪的節號即可。

我的條件：
- 可用資料集（含授權狀態；不確定的標「待確認」）：〔　〕
- 可用 GPU 型號、數量、單卡記憶體，以及可獨占多久：〔　〕
- 執行人力：〔例：我自己一人／1 位碩士生〕
- 目標會議與截稿日（必填；由我填，不要自行查或推測截稿日）：〔會議名稱、年份、截稿日〕
- 目標會議的論文類型：〔短論文（4 頁，如 ICASSP、Interspeech）／長論文（8 頁以上，如 ICLR、NeurIPS、ACL 主會）〕。
  短論文一個乾淨的貢獻就夠；長論文要概念層的主張加完整實驗與分析。§7 的題目大小與排序要配合這一點

結構（若篇幅受限：§0、§2、§3、§5、§7 不得縮減；可縮 §6、§8）：
0. 與第一輪報告的出入：深挖時發現第一輪判斷有誤、過時或過度簡化之處，逐條列出；
   沒有就寫「無」
1. 路線全景：從起源到現在的演進脈絡，用 Mermaid timeline 標關鍵論文與轉折點
2. 近 12–18 個月文獻盤點：先寫查詢式與篩選規則，再列論文，至少〔N，建議 20〕篇。
   每篇一行：機制、資料集、主要數字、與前作差異、是否開源（附 repo URL）。
   另以 CSV 程式碼區塊輸出，固定欄位：
   title,year,month,url,mechanism,dataset,main_metric,main_number,diff_from_prior,code_url,source_type
   （source_type 填 primary 或 secondary；欄位內不用逗號，改用分號）
3. 方法細節比較：挑 3–5 篇最重要的，比較架構、訓練方式、推論成本、失敗情境；
   用同一種畫法繪製各方法的 Mermaid 架構圖，附比較表
4. 失敗與被放棄的方向：哪些方法曾被嘗試但放棄、原因為何；每項附說出此事的來源，
   沒有來源的標【推論】
5. 基線與可復現性：哪些有可靠開源實作、復現難度、常見的坑；建議先復現哪一篇及理由，
   並列出「復現成功」的判準（對到論文的哪個數字、允許多少誤差）
6. 近六個月大廠動態：Google／Meta／OpenAI／Apple／NVIDIA 及此題目的主要業界玩家在此路線的
   發表與產品，作為「做到一半被做掉」的風險評估依據
7. 未解問題與具體題目：5–8 個 gap，對每個給出可執行題目：假設、方法、實驗設計、
   比較基線、所需資料、預估單次完整實驗的 GPU 小時、風險，以及下面兩項：
   (i) 最接近的 prior work：2–3 篇最像這個題目的論文，各一行「它做了什麼、和這個題目差在哪」，
       附 URL；找不到就寫查過的查詢式。這是審稿人會問的第一個問題
   (ii) Pilot 與放棄判準：一個 2 週內可做完的最小實驗（小資料、小模型、只跑一個 baseline 與提案方法），
       寫出「什麼結果算假設成立」「什麼結果就該放棄或改題」，數字要具體
   GPU 小時以論文自述的訓練時間與硬體為基準推算並列出算式，換算到我的 GPU 時
   說明換算假設；論文未報告者標「無依據」，不要估。
   依「與我的條件契合度 × 截稿日前能做完主實驗與消融」排序，畫成 Mermaid quadrantChart；
   排序時考慮論文類型：短論文偏好單一貢獻、一個主資料集；長論文要有分析面向與多資料集
8. 投稿規劃：以目標會議為主。先解剖它近兩年收的 3 篇同路線論文（要實際開過原文），
   每篇一列，表格欄位固定：論文（URL）／貢獻類型（新成分、新架構、新學習方式、新損失函數、新資料或評測、新分析）／
   baseline 數／資料集數／消融實驗數／主表的欄與列各是什麼／有無多 seed 或顯著性檢定／有無分析圖。
   從這張表歸納「這個會議在這條路線要什麼」，再寫：常見的拒稿理由、排序第一的題目要投它還缺什麼
   （對照上面那張表，缺幾個 baseline、缺哪種分析）；若截稿日前明顯做不完，列出下一個合適的場合

要求：
- 以英文來源為主：arXiv、頂會論文、GitHub；不納入中文來源。只列你實際開啟過的論文，
  每篇附開啟的 URL；僅從搜尋摘要或他文引用得知者另列並標「二手」。不要補全或猜測編號。
  不需附引用數
- 所有數字附來源 URL、測試條件與日期，用表格呈現
- 每個結論性主張標記：【共識】／【單篇】／【推論】。不確定處明說
- 示意圖用 Mermaid，總數 3–5 張；節點標籤不含括號、引號、斜線；每張圖前先用文字
  列出節點與邊。數字類內容一律用表格
- 以繁體中文（臺灣用語）撰寫，專有名詞保留英文。輸出 Markdown。以完整與可驗證為優先，
  不要為了精簡而省略論文
- 結尾兩項：
  (a) 搜尋紀錄與盲區：資料庫、查詢式、沒找到或無法存取的部分
  (b) 研究提案 one-pager：推薦的第一個題目，含問題、方法、實驗計畫，以及從截稿日倒推的
      時程（pilot、復現基線、主實驗、消融、初稿各留多少週），pilot 是第一個里程碑，
      並標出哪個里程碑趕不上就該改投下一個場合
```

## 操作方法（第二輪）

前提：第一輪已跑完並核對（`round1_map.md`），手上有 `<題目>_r1_<日期>_checked.md`。

### 研究生：先和教授談
1. 第二輪要填的條件（資料、GPU、目標會議）由教授決定；第一輪 §9 就是為那次討論準備的問題清單。
2. 帶去的東西：第一輪結尾 (b) 的 10 分鐘骨架、§3 路線地圖、§6 成熟度、§7 未解問題、§9 問題清單。先報你看懂了什麼，再問 §9 的問題。
3. 討論後記下：選定的路線（用報告裡的命名）、資料與 GPU、目標會議與截稿日。這些直接填進第二輪。

### 跑
4. 填條件五格。截稿日查會議官網填，不要讓模型查——它會給錯日期。論文類型看會議的 call for papers 頁數限制。資料集寫到授權狀態、GPU 寫到單卡記憶體與可獨占時間；不確定的寫「待確認」，不要猜。
5. 新對話，開啟 Deep Research 功能，附上 `_checked.md`，貼第二輪指令全文。若附件太長被截斷或無法附檔，改貼第一輪的一頁摘要、§3 路線地圖與結尾 (c)，並把指令中的「見附件」改為「摘要如下」。
6. 存成 `research/<題目>_r2_<路線>_<日期>.md`（在你的 repo 裡）；§2 的 CSV 區塊另存 `.csv`，之後用來篩選排序與排閱讀順序。

### 核對
7. 另開乾淨對話，用 `round1_map.md` 的核對指令。重點：§2 每一列、§5 的復現判準、§7 的 prior work 與 GPU 算式、§8 那 3 篇接受論文的數字、one-pager 的時程是否真的對得上截稿日。
8. §0 若列出與第一輪的出入，回頭改 `_r1_checked.md`。
9. **補工具的盲區。** Deep Research 常漏最近 1–2 個月的 arXiv、workshop 論文、只有 GitHub 的工作。報告核對完之後自己做兩件事：
   - 用 §7 排序前三的題目各組 2–3 個關鍵字，到 arXiv 搜近 2 個月的列表（arXiv 的 listing 或 advanced search 設日期），看前 50 筆標題；有像的開摘要。結果記進 §7 那題的「最接近的 prior work」
   - 在 Google Scholar 對 §5 建議復現的那篇與 §7 排序第一題最接近的 prior work 設 alert（「引用這篇的新論文」），之後每週掃一次。有人做了你的題目，通常會引用同一篇前作

### 之後
10. 研究生把 one-pager 給教授看，請教授決定題目與里程碑；教授改過的版本才是正式計畫，存 `research/one_pager_<日期>.md`。
11. 第一步照 §5 的建議復現一篇；復現數字對上論文之前不要開始改方法。
12. 摘要、投影片、單張圖重畫：各自另開一般對話處理，不放進研究指令。
13. 模板要改時直接改本檔，在文末修改紀錄加一行。
